Notification Framework

From notification chaos to a coherent system for communicating with users across severity levels and contexts

The Problem

Notification overload, no coherence

Dayforce had notifications everywhere. Success messages. Error alerts. System updates. Warnings. Confirmations. Every team implemented their own, creating a cacophony of competing attention-grabbers.

We had components—toasts, banners—but no framework for when to use what. No rules for severity. No guidance for detail level. No consistency.

Too Many Notifications
Toasts stacking on toasts. Banners competing for space. Users missing critical alerts in the noise.
Wrong Severity Mapping
"Employee updated" shown as error (red). Critical system failure shown as info (blue). No standards.
Inconsistent Detail Levels
Some toasts: one word. Others: full paragraphs. No way to provide context or actions when needed.
No Dismissal Strategy
Some auto-dismiss. Some require click. Some never go away. Users frustrated, confused.
Solution

A coherent notification framework

Rather than just providing components, we built a decision framework that maps notification purpose, severity, and context to the right pattern.

Two primary patterns
Toast
Temporary, non-blocking feedback. Auto-dismisses after 4-6 seconds. For confirmations and low-severity updates.
→ "Employee saved successfully"
→ "Report exported"
→ "Settings updated"
Banner
Persistent, contextual messaging. Stays visible until dismissed or resolved. For warnings, errors, and system-level updates.
→ "System maintenance in 1 hour"
→ "Failed to load payroll data"
→ "Required fields missing"
Framework Rule 01

Severity determines pattern + style

Success
User action completed successfully
TOAST
Color: Green (#00875A)
Icon: Checkmark
Duration: 4 seconds, auto-dismiss
Example: "Employee created successfully"
Info
Non-critical system updates or context
BANNER
Color: Blue (#0066CC)
Icon: Info circle
Duration: Persistent until dismissed
Example: "New feature available: Bulk timesheet approval"
Warning
Action needed, but not blocking
BANNER
Color: Yellow (#FF991F)
Icon: Warning triangle
Duration: Persistent, with action button
Example: "System maintenance scheduled for tonight at 2 AM"
Error
Action failed or data issue
BANNER
Color: Red (#DE350B)
Icon: Error X
Duration: Persistent until resolved
Example: "Failed to save employee. Check required fields and try again."
Framework Rule 02

Detail levels match user needs

Simple Toast
Title only. For straightforward confirmations where no additional context needed.
✓
Employee saved
Banner with Description
Title + supporting detail. For warnings or errors where users need more context.
⚠
System maintenance tonight
Dayforce will be unavailable from 2:00 AM to 4:00 AM EST for scheduled maintenance.
Banner with Action
Title + description + action button. For errors where users can resolve immediately.
✕
Failed to load payroll data
Connection timeout. Your internet connection may be unstable.
Framework Rule 03

Placement matches scope

Toast: Top-right
Global position. Visible but non-blocking. Stacks vertically (max 3 visible).
→ Confirmations
→ Success messages
→ Non-critical updates
Banner: Contextual
Placed above affected content. Page-level or section-level. Pushes content down.
→ System-level: Top of page
→ Form errors: Above form
→ Section warnings: Above section
Decision Framework

How teams choose the right pattern

1️⃣
Is this confirming a user action?
→ Yes: Toast (success)
2️⃣
Is this blocking the user from continuing?
→ Yes: Banner (error or warning)
3️⃣
Does the user need to take action?
→ Yes: Banner with action button
→ No: Toast or banner (depends on severity)
4️⃣
Is this system-wide or contextual?
→ System: Banner at page top
→ Contextual: Banner above affected area
