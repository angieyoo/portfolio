Loading States

Defining rules for a slow application—making wait times feel faster through better loading patterns

The Problem

Legacy app, lots of waiting

Dayforce is a legacy enterprise system. It's slow. Users encounter loading states constantly—opening pages, running reports, saving data, filtering tables. We can't magically make the backend faster, but we can make waiting feel better.

The problem: Every team handled loading differently. Some showed full-screen spinners. Some showed nothing. Some froze the UI. No consistency, no standards, no thought about what kind of loading pattern fits which context.

Full-Screen Blockers
Page loads showed full-screen spinners. Couldn't do anything else while waiting 3-5 seconds.
No Feedback
Some actions gave zero feedback. Click button, nothing happens, wait... did it work? Click again. Now it's double-submitted.
Wrong Patterns
Tables loaded with spinners instead of skeleton rows. Progress bars for indeterminate waits. No distinction between contexts.
Frozen UI
Some features just froze. Cursor turned to loading spinner, but nothing on screen indicated progress.
Solution

Context-appropriate loading patterns

We couldn't fix the performance. But we could define rules for which loading pattern to use when—based on context, duration, and user needs.

The Core Principle
Different types of loading require different patterns. Page loads need skeleton screens. Table refreshes need inline spinners. Long processes need progress bars. Button actions need loading states. Match the pattern to the context.
Pattern Library

Five loading patterns

Skeleton Screens
For: Initial page loads, table data loading
Why: Shows structure while loading. Less jarring than blank screen.
When: Page loads, table data fetching (>500ms)
Never: Button clicks, quick actions (<500ms)
Inline Spinners
For: Localized loading, component refreshes
Why: Minimal, unobtrusive. Doesn't block entire UI.
When: Card refreshing, section reloading, search results updating
Never: Full page loads (use skeleton instead)
Progress Bars
For: Determinate processes with known duration

Step 3 of 5: Calculating deductions
Why: Shows progress + time remaining. Reduces anxiety.
When: File uploads, report generation, batch processing
Never: Unknown duration (use spinner instead)
Button States
For: Action feedback, preventing double-submit

Loading
Why: Clear feedback that action is processing. Prevents double-submit.
When: Any button that triggers async action (save, submit, delete)
Never: Navigation buttons (instant actions)

Decision Framework

Choosing the right pattern

Context Duration Pattern Reason
Page load >500ms Skeleton Shows structure, reduces perceived wait
Button click Any Button loading Immediate feedback, prevents double-submit
Table sort/filter >300ms Dim + spinner Less disruptive than replacing all data
Card refresh >500ms Inline spinner Localized, doesn't block other content
Report generation >5s, known Progress bar Shows progress, reduces anxiety on long waits
Search results <300ms None Too fast, loading state would flash
Rules & Guidelines

When to show loading states

Rule 1: Delay threshold
Don't show loading states for actions <300ms. Loading indicator would flash, making UI feel slower. Show loading only if it takes >300ms.
Rule 2: Preserve context
Don't replace content with spinners. Dim existing content + show loading indicator. Users maintain context of what they were looking at.
Rule 3: Show structure early
For page loads, show skeleton of final layout immediately. Don't show blank screen then pop in content. Progressive disclosure feels faster.
Rule 4: Prevent double-actions
Always disable buttons during loading. Show loading state. Prevents users from clicking again and double-submitting.
Rule 5: Match duration to pattern
Quick actions (<2s): Spinner. Medium (2-5s): Skeleton or inline spinner. Long (>5s): Progress bar if determinate, spinner + message if not.
